# 공식 예제 제작 목록과 출시 검사

`catalog/official/catalog.json`은 합의한 **프로젝트 120개·자료 및 도구 120개**의 제작 명세입니다. 모든 최초 항목의 상태는 `planned`이며, 실제 콘텐츠나 검증 기록을 생성했다는 뜻이 아닙니다. 초기 사용 가능 수와 게시 수는 모두 **0**입니다. 서비스 화면의 공식 예제 목록으로 이 파일을 그대로 노출하거나 시드하지 않습니다.

```powershell
node tooling/run-pnpm.mjs exec tsx tooling/catalog/generate-contracts.ts --check
node tooling/run-pnpm.mjs exec tsx tooling/catalog/generate-inventory.ts --check
node tooling/run-pnpm.mjs exec tsx tooling/catalog/cli.ts
node tooling/run-pnpm.mjs exec tsx tooling/catalog/cli.ts --release
```

앞의 검사는 목록이 일관된 제작 명세인지 확인합니다. 마지막 명령은 검증·게시된 프로젝트 120개, 자료 120개, 프로젝트의 실제 호스트 사용 조합 360개가 모두 있어야 종료 코드 0을 반환합니다. 아직 제작하지 않은 현재 목록에서는 종료 코드 1이 정상입니다.

## 제작과 증거의 경계

1. `planned`: 원문 이름, 목적, 연결, 입력·결과, 검증 기준을 보존합니다. 파일·검증·검수 완료 기록을 넣을 수 없습니다.
2. `implemented`: 운영 콘텐츠 폴더의 모든 파일과 원본 바이트 해시를 고정합니다. `workflow.json` 또는 `resource.json`, 사용 설명, 이용 조건이 필수입니다. 테스트용 제공자·개발용 폴더·비밀 환경 파일을 운영 콘텐츠에 넣지 않습니다. 아직 사용 가능 수에 포함하지 않습니다.
3. `verified`: 설치된 기능 목록, 파일 무결성, 실제 모델·외부 서비스 사용, 실제 호스트 진입 및 결과 회수, 목적별 검증 기준을 모두 충족해야 합니다. 세 호스트별로 독립된 실제 사용 기록이 필요합니다.
4. `published`: 동일한 산출물 해시에 대한 검수자·검수 시점·고유 목적 확인이 추가로 필요합니다. 실제 서비스 게시·철회는 별도 P4 운영 계층의 권한과 트랜잭션이 처리합니다. 이 도구가 게시하지는 않습니다.
5. `suspended`: 무결성 검사는 계속하되 사용 가능·게시 수량에서 제외합니다.

`official-example.schema.json`, `verification-record.schema.json`이 데이터 계약의 원본입니다. `generate-contracts.ts`가 TypeScript를 생성합니다. 스키마가 변경되면 루트 `generate:spec`도 실행하여 전체 번들을 재생성합니다. 목록의 의존성은 제작 시작점의 최소 요구사항이며 실제 콘텐츠가 새 연결·기능을 요구하면 추가해야 합니다.

## 파일 규칙

프로젝트 폴더는 `workflow.json`과 실제 운영 자료를 포함합니다. 자료는 루트의 `resource.json`이 `SKILL.md`, 지침, 문서, 코드·템플릿 등의 해시를 고정하며 `ResourceDescriptor` 계약을 따릅니다. 전이 의존 자료는 `resources/<alias>/resource.json`과 그 파일들을 포함합니다. 디렉터리의 파일 전체를 목록에 적으며 숨은 파일, 심볼릭 링크, 경로 이탈, 대소문자 충돌을 거부합니다.

검증 기록과 실제 실행 증거는 운영 콘텐츠 폴더 **밖**에 보관합니다. 증거에는 비밀 키나 고객 원문을 포함하지 않도록 수집 시점에 가려야 합니다. 검사 도구는 경로·원본 해시·현재 검증 기준·실제 의존 사용·호스트 진입·결과 회수·90일 이내 증거를 확인합니다. 만료 시 재검증이 필요합니다.

## 신뢰된 검증자

검증 기록은 `signature` 필드를 제외한 canonical JSON에 대한 Ed25519 서명을 요구합니다. 검증 키는 카탈로그에 들어 있는 키를 신뢰하지 않으며 운영자가 `--trusted-keys <key-id-to-public-pem.json>`으로 공급합니다. 설치·검증된 기능 목록은 별도의 `--capabilities <capabilities.json>`으로 제공합니다. 기본 목록은 P2의 입력·AI·결과 세 블록뿐입니다.

이 검사만으로 모델이 실제 실행되었다는 사실을 독립적으로 관측할 수는 없습니다. 신뢰된 검증자가 실제 실행을 관측하고 목적별 기준을 확인한 뒤 서명해야 합니다. `mode: real`이라는 문자열만 쓴 파일, 자체 서명 키, 모의 제공자 기록, 가짜 성공 플래그, 오래되거나 다른 파일의 증거는 사용할 수 없습니다. 신뢰된 검증자 키의 발급·보관·철회와 실제 실행 증거 수집은 운영 검증 인프라의 책임입니다.

검사기는 모델·외부 서비스를 호출하지 않고 읽기 검증만 합니다. 내부 단위 시험은 임시 폴더와 일회성 테스트 키로 검사기의 거부 동작을 검증하며, 그 결과는 공식 예제의 실제 실행 증거로 등록하지 않습니다.
