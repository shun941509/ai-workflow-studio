# Run-local vector and hybrid search contract

Status: implemented backend with deterministic provider-boundary tests and actual local storage/search/HTTP/MCP execution. Live OpenAI execution is unverified; no account, key creation, or paid request is part of this change. Keyword/vector/hybrid authoring and fixed embedding connections are described in [the UI contract](rag-authoring-ui.md). The separate optional [reranker contract](rag-reranker.md) does not change this embedding identity. Agentic RAG, GraphRAG, hosted vector databases, arbitrary models and external uploads remain outside this implementation.

## Fixed request and generation identity

`knowledge.build` accepts `profile: local-run-embedding-v1`, `indexSettings.kind: vector | hybrid` and an existing `embeddingProfile` model alias. The alias must declare `kind: embedding` and bind to a local DPAPI-backed embedding profile. The only supported model is `text-embedding-3-small`, requested with `dimensions: 256`, `encoding_format: float`. The service normalizes finite, nonzero vectors to L2 and searches with cosine. A generation permits at most 128 chunks / 32768 vector components. Chunk boundaries retain the existing UTF-8 byte provenance. The index binds every vector row to its original chunk SHA-256.

The embedding identity includes provider/model, dimensions, metric, normalization, verbatim preprocessing, the full pinned cl100k_base tokenizer fingerprint, the local profile ID and workflow alias. OpenAI does not document an immutable weights snapshot for this model. `modelRevision: unversioned-provider-alias` explicitly records this limitation: a matching fingerprint proves the same request/processing contract, not identical upstream weights over time. Response model identity must match exactly. Query embedding uses the same saved generation profile and immutable resolved-plan binding; an altered binding, tokenizer or dimension fails closed.

## Token reservation and disclosure

The [Embeddings API](https://developers.openai.com/api/reference/resources/embeddings/methods/create) accepts bounded text arrays and reports prompt/total token usage. Its reference does not provide an embedding input-count endpoint. The [embedding guide](https://developers.openai.com/api/docs/guides/embeddings) documents model limits and shortened dimensions. These were checked on 2026-10-28.

The local measurement is js-tiktoken 1.0.21 / cl100k_base with special-looking tokens treated as ordinary text, no Unicode normalization and no malformed surrogates. Each input reserves `max(local BPE count, UTF-8 byte length) + 64`; requests contain at most 16 inputs, at most 8192 reserved units per input and 32768 units per request. The byte-based allowance and padding are a conservative application policy, not a billed token count or cost guarantee. Local BPE count, reservation rule/fingerprint and actual reported usage are recorded separately without source text. A reported usage above the reservation is charged and immediately blocks further work. Missing/malformed usage retains the whole reservation and requires attention.

Every build batch and query shares the existing atomic root model-call/token budget (normally 100 calls / 200000 tokens). Actual successful usage settles that reservation; confirmed 4xx rejection may settle zero, while transport loss, 5xx, malformed responses and cancellation after send are unknown. No automatic retry, retry-after sleep or replay follows any embedding request; a 429 stops the operation and requires an explicit new run. This avoids repeating a partly built generation. The Responses remote-count protocol is unchanged.

The embedding endpoint receives each selected chunk or query. Local-only means original files, immutable generations and search remain inside this run's local managed storage; it does not mean embedding text stays offline. Credentials come only from the existing DPAPI store and never enter generation metadata, CLI arguments, ZIPs or logs. The endpoint/origin is fixed and redirects are denied.

### Synchronous tokenizer work limits

Testing exposed a real JS BPE worst case: nine 8000-character repeated-word pieces consumed about 78 seconds synchronously. AbortSignal/timeouts cannot interrupt that function. Both embedding cl100k_base and existing context o200k_base now inspect the pinned encoding's actual regex pieces **before** BPE: one encoding permits at most 64 KiB, 8192 pieces, 512 UTF-8 bytes per piece and a sum of squared piece byte lengths of 262144. A complete build preflight, embedding batch, or context-building operation permits cumulative 256 KiB, 32768 pieces and squared-byte work 1048576; context trials count their repeated prefixes every time. The complete build's work is inspected before its first encoding/provider call. Oversized work is rejected explicitly; it is never approximated, silently truncated, moved to an unisolated worker or advertised as a hard OS execution deadline. Encoding token IDs and the existing local context fingerprint remain unchanged for admitted text.

## Atomicity, permissions and repeat behavior

All source files are current-run registered FileRefs whose bytes are reverified. All chunks and batching limits are validated before the first external call. Complete vectors are required before immutable staging and activation CAS. A failed/interrupted batch cannot expose a partial active index. An uncertain operation cannot auto-replay after restart. Completed builds reuse their fixed reference; completed search repeats are rejected for vector/hybrid because re-embedding would create a second paid side effect. Keyword repeats remain current-ACL recomputations.

Current subject/group membership, document ACLs and tombstones filter scoring and are checked again after asynchronous embedding, fusion and citation construction. Hybrid runs both channels against one pinned generation, combines normalized ranks using configured RRF, and reauthorizes before returning whole source chunks. No private global query/vector cache exists.

## Validation gate

Required evidence: fixed-model/tokenizer/dimension rejection; strict provider schema and batch limits; zero-key/live-network tests; shared budget exhaustion and parallel reservation; 429 no retry; unknown/missing usage reservation retention; current ACL/group/tombstone filtering during an embedding await; no partial active generation; immutable source/vector hashes; durable restart with no automatic calls; three host ZIPs through actual file upload/build/query; HTTP/MCP service boundary parity. Live provider model quality, upstream model immutability and paid usage accuracy remain unverified.

Confirmed tests cover the above backend boundaries. The model substitute exists only inside test sources; production always uses the fixed OpenAI endpoint and DPAPI. The real MCP server's initialize/validate/start/results handlers were exercised against a real loopback daemon; initialization and validation produced zero embedding calls.
