# 실행 요청 ID와 응답 유실 복구

R-02의 범위는 브라우저에서 시작한 하나의 실행 의도를 같은 `requestId`와 같은 요청 본문으로 유지하는 것이다. 서버가 작업을 접수한 뒤 HTTP 응답이 유실되어도 브라우저가 묵시적으로 다른 실행을 만들지 않는다. 이 규격은 실행 중 모델/외부 서비스 호출의 결과 확인이나 프로세스 중단 후 전체 실행 재개를 대신하지 않는다.

## 확인한 결함과 실제 재현

수정 전 `PackagePage`는 제출할 때마다 `crypto.randomUUID()`를 호출했다. 실패 후 입력과 준비 상태는 남았지만 요청 ID는 사라졌다. 실제 React 화면·운영 ZIP·SQLite·인증 HTTP를 사용한 회귀 시험에서 첫 POST가 202로 접수된 뒤 브라우저로 가는 응답만 끊었다. 다음 제출에 다른 UUID가 생겼고 실제 run은 2개였다. 서버의 같은 ID 멱등 처리가 깨진 것이 아니라 화면이 재시도를 새 요청으로 보낸 문제였다.

시험의 첫 하네스 실행은 `route.fetch`가 같은 출처 메타데이터를 보존하지 않아 401을 받았다. 이를 수정해 실제 브라우저 쿠키/CSRF와 `sec-fetch-site: same-origin`을 전달한 뒤 위 202 접수·2개 실행을 재현했다. 401을 중복 실행 증거로 집계하지 않는다.

## 저장과 전송 경계

- 새 요청은 UUIDv4를 발급하고 `localStorage`에 `studio-run-request:v1:<UUID>` 키와 `pending` 값만 기록한다. 읽어 다시 확인한 뒤에만 POST한다.
- 입력 본문, 모델 연결 ID/별칭, 패키지 ID, 본문 해시, API 키, 인증 쿠키, CSRF, 실행 결과는 이 저장소에 기록하지 않는다. 저장되는 UUID는 비밀 인증 수단이 아니며 조회에도 기존 Runner 인증이 필요하다.
- 처음 보낸 JSON 문자열은 현재 페이지의 메모리에만 보존한다. 같은 요청 재시도는 이 문자열에서 동일한 본문을 만들며, 이후 화면에서 편집한 값이나 호출자가 수정한 객체를 읽지 않는다.
- JSON 요청은 서버와 같은 8 MiB 상한을 적용한다. 저장 읽기/쓰기/읽어 확인 실패는 새 POST 전에 차단한다. 잘못된 UUID, 손상된 값, 미래 버전의 기록도 조용히 버리고 실행하지 않는다.
- 최대 32개의 미확정 ID를 보존하며 자동 만료하지 않는다. 항목별 키를 사용하므로 다른 탭의 기록을 목록 덮어쓰기로 지우지 않는다. 각 새 작업 전에 저장소를 다시 읽으며 다른 탭의 변경도 화면에 반영한다. 여러 탭에 대한 분산 잠금이나 모든 동일 입력의 중복 제거를 보장하는 기능은 아니다.

## 상태와 사용자 행동

|상태|허용 행동|저장/전송 결과|
|---|---|---|
|미확정 기록 없음|입력·연결 준비 후 실행|UUID를 저장한 뒤 최초 POST|
|응답 실패/손상/30초 초과, 원문이 메모리에 있음|접수 여부 확인 또는 같은 요청으로 재시도|기존 UUID·같은 본문 사용. 입력 편집은 기존 요청을 바꾸지 않음|
|새로고침 후 미확정 ID 있음|자동 접수 조회, 수동 재조회|입력은 저장하지 않았으므로 자동 POST/재구성 없음|
|조회 결과 `not_found`|기록을 유지하고 재조회|현시점의 기록 부재이며 미실행 확정이 아님. 이전 POST가 뒤늦게 접수될 수 있음|
|유효한 POST 응답 또는 조회 `found`|접수된 실행 열기|run ID 확인 후 미확정 기록과 메모리 본문 제거. 제거 실패 시 UUID가 남아 다음에 재조회 가능|
|사용자가 별도 실행을 명시적으로 선택|변경한 입력·연결을 준비해 새 실행|새 UUID 발급. 기존 미확정 ID 유지. 이전 실행을 취소하지 않고 동일 작업이 중복될 수 있음을 안내|

서버 응답 대기는 시작과 조회 각각 30초다. 이 시간 제한은 브라우저의 대기를 끝낼 뿐 서버 작업을 취소하거나 미실행으로 판정하지 않는다. 늦게 도착한 응답이 미확정 기록을 조용히 지우지 않는다. 동일 요청의 확인/재시도는 동시에 진행하지 않으며, React의 `busy` 상태가 그려지기 전 연속 제출도 ref로 막는다.

확인 전 일반 실행 버튼을 누르는 것으로 새 요청을 만들 수 없다. 별도 실행은 명시적인 선택과 새 준비 과정을 거친다. 사용자가 동일 입력을 의도적으로 다시 실행하는 경우까지 금지하지는 않는다.

## 서버 조회 계약

통합 담당자가 추가한 인증 API는 `GET /api/run-requests/:requestId`이다. UUIDv4만 허용하고 기존 `request_id` 인덱스에서 직접 조회한다.

```json
{ "state": "found", "runId": "run_cccccccc-cccc-4ccc-8ccc-cccccccccccc" }
```

```json
{ "state": "not_found" }
```

응답은 `no-store`이며 입력·결과·프로필을 조회하거나 반환하지 않는다. 최근 50개 실행 목록으로 ID 존재 여부를 추정하지 않는다. RAG 본문 공개가 차단되어도 최소 실행 식별값을 확인할 수 있으며 실제 상태/결과 열기는 기존 권한 검사를 따른다. 네트워크/인증 오류와 잘못된 응답은 `not_found`로 변환하지 않는다.

## 범위와 제한

- 이 복구 기록은 브라우저 프로필과 **동일 origin(스킴·호스트·포트)**에 속한다. Runner 주소/포트나 브라우저 프로필이 바뀌면 이전 origin의 기록을 자동으로 찾지 못한다. 그 경우 이전 주소 또는 Runner 실행 기록에서 확인해야 한다. 브라우저 저장소를 사용자가 삭제한 경우도 복구 정보가 사라진다.
- 동일 origin이 다른 Runner 데이터 저장소를 가리켜도 `not_found`만으로 기존 ID를 삭제하거나 자동 재실행하지 않는다. 이 변경은 서로 다른 설치 간 이전 실행을 검색하는 기능이 아니다.
- 새로고침 후에는 입력을 재입력해도 기존 요청 본문과 같음을 증명할 자료를 브라우저에 보관하지 않는다. 따라서 해당 ID는 조회만 가능하며, 재입력한 내용을 과거 요청으로 자동 전송하지 않는다.
- 실행 접수 이후 모델/외부 작업의 결과 불명, 과금 예약, 프로세스 crash, 보상은 기존 Runner 실행·원장 정책을 따른다. 이 기능은 외부 쓰기의 exactly-once 보장이 아니다.
- 미확정 요청에 대해 사용자가 명시한 별도 실행은 두 실행을 만들 수 있다. 이를 정상 재시도의 중복 방지와 구분해 화면에서 설명한다.
- 이번 검증에는 실제 유료 모델/API 키/외부 서비스 호출이 없다. 운영 빌드·전체 회귀는 통합 담당자의 별도 단계다.
